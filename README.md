# shop-broken-tdd — учебный репозиторий

Лабораторная работа по шести темам: **форматтеры**, **линтеры**, **типы**,
**CI**, **тестирование с TDD** и **LLM-агенты**.

Репозиторий специально приходит в «красном» состоянии: сборка в CI падает, часть
тестов красная, две функции-заглушки не реализованы. Ваша задача — починить
сборку, а затем реализовать расчёт суммы заказа по TDD, с LLM-агентом в роли
исполнителя.

Используемый стек: **uv** (зависимости и виртуальное окружение), **ruff**
(форматирование и линт), **mypy** (типы), **pytest** (тесты), **GitHub Actions** (CI).

## Быстрый старт (Ubuntu)

```bash
git clone <url-репозитория> && cd shop-broken-tdd
./scripts/setup.sh      # поставит uv, Python 3.12 и зависимости
./scripts/check.sh      # локальная копия всех проверок CI — сразу будет красной
```

Подробная инструкция, включая ручную установку и разбор типовых проблем:
[`docs/00-environment.md`](docs/00-environment.md).

## Предметная область

Это небольшой фрагмент системы интернет-магазина со складским учётом. Магазин
продаёт товар, который лежит на складах: кладовщик видит остатки, менеджер — что
заканчивается, покупатель — итоговую сумму заказа с доставкой и НДС.

Круг пользователей и его запросы:

| Кто        | Что делает в системе                                   |
| ---------- | ------------------------------------------------------- |
| Кладовщик  | пополняет склад, резервирует товар под заказ, списывает |
| Менеджер   | смотрит стоимость запасов и здоровье запасов             |
| Покупатель | собирает корзину, применяет промокод, платит             |
| Налоговая  | получает НДС, начисленный на заказ                      |

Модули в `src/shop/` разбирают этот круг по частям:

* `money.py` — деньги. Суммы хранятся в целых копейках, проценты считаются
  целочисленно с округлением «половину вверх». Это эталон стиля: его не трогают.
* `inventory.py` — склад. Остатки по артикулам, резерв под конкретный заказ,
  списание брака, порог низкого остатка, по которому товар считается
  заканчивающимся.
* `reporting.py` — отчёт для менеджера: суммарная стоимость запасов и их
  состояние, всё в одной текстовой строке на склад.
* `checkout.py` — оформление заказа. Позиции с артикулом, количеством и ценой,
  ярусные скидки за объём, промокод, потолок скидки, стоимость доставки в
  зависимости от города и НДС сверху.
* `specs/checkout.md` — бизнес-ТЗ на расчёт суммы заказа. Источник истины.

Связка между модулями простая: товар приходит со склада выгрузкой (отсюда
строковые значения в позициях заказа), попадает в корзину, резервируется на
складе, а покупателю показывается сумма с доставкой и НДС.

Два решения, которые выглядят странно, пока не знаешь предметную область:

* **Никаких `float` и `Decimal`.** Деньги — целое число копеек: `0.1 + 0.2 != 0.3`,
  а счёт нельзя закрыть на копейку раньше или позже.
* **Значения позиций — строки.** Данные приходят из складской выгрузки, их удобно
  проверять целиком, не разбирая типы на границе. Числом значение становится там,
  где формуле нужна арифметика.

## Устройство CI

Два независимых workflow, каждый со своими джобами:

* `part1-ci.yml` → `format`, `lint`, `types`, `tests` (тесты части 1 на Python 3.12
  и 3.13);
* `part2-ci.yml` → `tests`, `checkout-coverage` (не ниже 90 % покрытия
  `shop.checkout`), `tdd-history` (проверяет, что тесты написаны раньше кода).

Команды CI и команды скриптов **одина в один**: `./scripts/check.sh` запускает все
проверки пайплайна, а `./scripts/check-part1.sh` и `./scripts/check-part2.sh` —
его части. Это главный навык работы: чинить сборку локально по выводу
инструментов, а не в веб-интерфейсе GitHub.

## Правила проекта

В проекте намеренно **нет классов и исключений**: данные — это словари и списки,
некорректный вход возвращается через `None` и ранний `return`. Придерживайтесь
этого стиля и в своём коде, и в промптах для агента — иначе проверки не совпадут
с тем, о чём их читает `docs/01-toolchain.md`.

Правила для LLM-агента вынесены в [`AGENTS.md`](AGENTS.md).
